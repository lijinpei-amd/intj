# Lazy launchers Task 1: uniform bound-launcher header (index 0)

Benchmark gate for Task 1 of `docs/superpowers/plans/2026-09-27-lazy-dynamic-launchers.md`
(every bound object is one fixed `intj_bound_header` plus trailing arrays; no
behaviour change). Baseline: `2026-09-27_lazy-baseline_0_f507cfc.md`.

## Environment

- Candidate: `5ad90c08b633363cb5ed1649ace3a1db3758c43f` (branch `develop`), clean checkout.
- Baseline: `f507cfc` (`/tmp/intj-bench/lazy-baseline`); A/B base: a detached
  worktree of `24bf5d1` at `/tmp/intj-lazy-base` (same code as `f507cfc`; only
  docs/journals differ).
- CPU: `taskset -c 0`, one process at a time. Shared host; 1-min load average
  24.01 at the start of `lazy-task1` (other users), 3.27 at its end; 2.91 / 3.18
  around `lazy-task1-rerun`. A/B files log `/proc/loadavg` per process.
- GPU: AMD Instinct MI308X (`gfx942`), GPU 0 (`HIP_VISIBLE_DEVICES=0`), tests ran on GPUs 1,2.
- Python 3.12.3 (`/tmp/gb2/bin/python`), Torch `2.14.0+rocm7.2`, Triton `3.8.0`, g++ 13.3.0.
- `INTJ_BENCHMARK_ROOT=/tmp/gbench`. CUDA: untested (no NVIDIA GPU).

and `taskset -c 0`: `benchmarks/bench_launch.py --last-key --iters 100000 --batches 9`
and `benchmarks/bench_intj_ffi_paths.py --mode all --iters 1000 --batches 9`.

Every one of the 60 gate files has `exit_status=0`.

## Result

Bound rows are 1-3 ns faster on the host (`bound pointer` -3.3 ns, `bound tensor`
-2.9 ns, `fixed device map/no-map` -1.1/-1.2 ns): the entry reads `bound->state`
instead of calling `PyModule_GetState(bound->module)`.

Four rows were flagged in the first run and three again in the rerun, all **unbound**
launchers (`module.entry`), whose source Task 1 does not change:

| row | baseline | lazy-task1 | rerun |
|---|---:|---:|---:|
| launch_last_key 32 alternate | 103.3 | 108.0 | 107.9 |
| launch_last_key 32 repeat | 99.0 | 103.8 | 103.9 |
| ffi_paths INTJ adapter kwargs | 105.8 | 110.2 | 110.2 |
| ffi_paths INTJ FFI wrapper kwargs | 125.8 | 129.6 | 129.4 (+2.9%, below threshold) |

The interleaved A/B reproduces them (below). **Cause: code placement, not code.**
The rendered 32-argument module's `intj_call` and `entry` compile to the same
instructions in both trees (7501 disassembly lines each; the 14 differing lines are
register renames and one `nopw` -> `nop`). The bound functions ahead of them
changed size, so `intj_call` moved from `0xac10` to `0xadb0` (`0x10` -> `0x30` mod
64). Rebuilding both trees' modules with `-falign-functions=64` (a local,
uncommitted edit to `_build_flags`, reverted) removes the gap: last_key 32 is
98.8/98.6 and 103.2/103.1, adapter kwargs 108.3/105.7. Accepted as layout noise;
not fixed in this task.
