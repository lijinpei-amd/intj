Each aggregate is the median of three process results. TVM FFI utility
scripts use 1,000,000 calls per row and `time.time()` (one mean per process);
INTJ utilities use nine batches of 10,000 calls, reporting each process's
median. Their common zero-argument Python measurement wrapper adds overhead
to absolute call times. The GPU script uses nine 1,000-call batches with a
host timer stopped before GPU synchronization, so the launch numbers include
host enqueue and possible GPU queue backpressure but exclude completion.
Arguments, kernels, compiled modules and TVM FFI TensorViews are prepared
before each timing loop.

## Aggregate: median of three process results

### HIP adaptation of the CUDA CUBIN example

The HIP benchmark compiles Triton `empty_kernel` with three pointers,
`n=128`, `BLOCK=128` and one program. It passes that HSACO directly to
`hipModuleLoadData`, then loads `empty_kernel` with `hipModuleGetFunction`
and launches with `hipModuleLaunchKernel`. INTJ reuses the **same compiled
function handle**, and Triton uses the source compiled-kernel object.
All three process rounds report HSACO SHA-256
`df3e529e178196ad62f7c07ab8593ede5b8596c76e7c6fbd12a5d947a696e65c`
and one INTJ compile callback before timing; block size is 256, shared memory zero.

| Case | µs/call |
|---|---:|
| TVM FFI HIP HSACO | 3.2598 |
| Triton same HSACO | 16.0320 |
| INTJ same function | 3.0526 |

TVM FFI checks 1D shapes on each call and receives preconverted
TensorViews; INTJ receives Torch tensors and takes the stream as an
argument. The CUDA CUBIN example is still CUDA-only; this HIP path
compares an actual identical AMD code object. The older HIP comparison
used different binaries.

The original TVM FFI script wraps a **Python function that does nothing**:
direct 54.92 ns, generated keyword wrapper 92.45 ns (+37.53 ns). The
INTJ script times a **host-only C launcher** with three integers: direct
67.70 ns, manual Python keyword adapter 107.50 ns (+39.80 ns). Of the

their unlike baselines. Applying TVM FFI's generated wrapper to the
**same INTJ launcher** costs 126.50 ns; the hand-written adapter costs
107.50 ns. They accept different control-argument signatures, so this
last difference is a property of these two wrappers, not a TVM FFI
versus INTJ launcher result. INTJ itself rejects native keyword calls.

### Dataclass unpacking: controlled INTJ calls

| Case | ns/call |
|---|---:|
| INTJ pair direct | 69.50 |
| INTJ pair prebuilt *tuple | 143.20 |
| FFI unpack Pair only | 165.70 |
| INTJ pair manual unpack | 179.00 |
| INTJ pair FFI unpack | 320.50 |
| INTJ pair stdlib astuple | 1172.20 |
| INTJ config direct | 83.70 |
| INTJ config FFI unpack | 331.10 |

The original `unpack_dataclass_to_tuple(Config)` row times conversion
**alone** (137.37 ns). The INTJ 320.50 ns row includes that conversion,
starred positional expansion and an INTJ call. Its two-field breakdown:
direct 69.50 ns → prebuilt `*tuple` 143.20 ns (+73.70) → per-call
manual tuple 179.00 ns (+35.80) → TVM FFI unpack 320.50 ns (+141.50).
That last increment is close to TVM's separately timed converter cost.
CPython 3.12 disassembly showed the direct call uses `CALL` while the
starred call uses `CALL_FUNCTION_EX`; building the tuple is also inside
the latter timing boundary. INTJ rejects dataclass objects natively,
so this comparison exercises an **application-level conversion**.
