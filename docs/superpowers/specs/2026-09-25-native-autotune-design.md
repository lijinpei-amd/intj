# Native Autotuned Launcher Design

## Goal

Let `make_launcher` accept a limited Triton `Autotuner` and use intj's native cache-hit path after tuning. A warmed call decodes current arguments, finds the selected kernel, evaluates its grid, and launches without Python binding, tuning-key construction, or a Python callback. Triton still benchmarks and selects on a miss. This removes the remaining decorated-Triton hot path from Aiter FlashKDA's opt-in multi-config K1 and K2 calls; `intj.compat.launch` remains a migration bridge for other decorated kernels.

Triton 3.7.1 and 3.8.0 make a tuning key from the decorator's named key values, followed by dtype strings of dtype-bearing arguments. Candidate order affects tie-breaking. The original tuner's cache omits device and target, so a bound native launcher needs its own selection state. `intj.compat.launch` already redirects a copied autotuner's inner launch to intj, but still performs Python tuning work on every call.

## API and first supported subset

`make_launcher(tuner, ...)` accepts an exact `triton.runtime.autotuner.Autotuner` with at least two configs and a bare `JITFunction` as `tuner.fn`. `bind_device=True` is required. The returned factory's `.bind_device(device)` produces the existing positional native callable: `grid_arg=N` prepends N grid dimensions, while `grid_cpp=annotated_def` prepends its keyword-only grid extras. Config-supplied JIT `constexpr` parameters are absent from that call. `return_compiled=True` returns the selected `CompiledKernel`; `torch_access`, `kernel_cache`, fixed `options`, and fixed `extra_annotation` keep their existing meanings. One-config callers keep the raw-JIT path.

The first subset requires `grid_arg` or `grid_cpp`. It refuses `grid_py`, `no_gpu`, `dynamic_options`, bound tensor/pointer parameter annotations, and an outer `Heuristics` wrapper. KDA must pass its inner K1 tuner and explicitly supply `IS_VARLEN = cu_seqlens is not None` and `HAS_BIAS = dt_bias is not None`, which the outer wrapper currently computes.

Every config must be an exact Triton `Config` and have the same `Config.kwargs` names; each name must identify a raw-JIT `constexpr`. Each value must be an exact `int` within signed 64 bits or an exact `bool`, with one stable type per name across configs. These values are supplied only by the selected config. Fixed annotations may bake other parameters, such as KDA's cache modifiers, but cannot bake a config-owned name. `num_warps` and `num_stages` may vary as exact positive integers; every config must have `num_ctas=1`, `maxnreg=None`, `ir_override=None`, and `pre_hook=None`. Validate each candidate's compiler options with the backend before provisioning. Reject fixed `options` for any config-owned compiler option (`num_warps`, `num_stages`, `num_ctas`, `maxnreg`, or `ir_override`) instead of merging duplicate keywords.

Reject a raw-JIT parameter named `grid`, `warmup`, `device`, `stream`, `device_type`, `warp_size`, or any compile-option field of the target backend. These names collide with `JITFunction.run` controls or `Config.all_kwargs()` when the cold callback reconstructs keyword arguments; the rule also covers config-owned `constexpr` names.

Every named tuner key must be a JIT parameter whose call-time value is an exact signed-64-bit `int` or `bool`. Dtype-bearing arguments may be supported Torch tensors/parameters or `None`; reject any other object with a `dtype` attribute. Refuse custom pruning (`early_config_prune` or `perf_model`), custom/deprecated benchmark controls (`do_bench`, `warmup`, `rep`, `use_cuda_graph`), reset/restore lists, user pre/post hooks, JIT pre-run hooks, active Triton launch hooks, an active autotuning listener, active stages-inspection or JIT cache hooks, asynchronous compilation, and interpreter mode. Refuse at construction when visible and again on a cold miss where state can change. As with raw intj, callers rebuild a warmed handle after changing Triton knobs or JIT source; Aiter checks interpreter mode and its knob key before reusing a handle. Standard Triton benchmarking and optional disk cache remain on misses. Python 3.10+, Triton 3.7.1/3.8.0, HIP, and CUDA compilation are in scope.

For config-dependent grids, the existing annotated `grid_cpp` function is the single grid formula. For example:

```python
def segment_grid(W: int, H: int, BW: int, *, num_segs: int):
    return (triton.cdiv(W, BW), num_segs * H)
```

`W` and `H` come from current JIT arguments, `BW` from the selected config, and keyword-only `num_segs` is a native-call grid extra. A grid parameter's annotation must match the exact type of its config-owned field. Extend the current restricted-AST, no-free-variable grid lowering to read config fields from the selected record after cache lookup. Expose the same generated C evaluator to the cold callback for candidate grids; benchmarking must not call a mutable Python function that could diverge from the native hit grid. KDA K1 uses `grid_arg=2` because its grid does not depend on the config.

## Key, module, and state ownership

Within one bound launcher and its fixed selection state, the native key must refine **both** the JIT specialization key and Triton's tuning key:

> same native key implies the same Triton compiler input and the same selected config.

Build normal intj specialization fields **only for caller-supplied JIT arguments**. A config-owned `constexpr` such as `BW` has no public call slot and contributes no key field before selection. Add the full typed value of each named scalar tuner key where the existing specialization key does not already preserve it exactly; KDA K2's ordinary `NUM_SEGS_CLASS` is the required example. Preserve dtype and `None` distinctions for every dtype-bearing JIT argument, using existing descriptor fields where sufficient. The key may be finer than Triton's, never coarser for specialization or config choice. Inject config-owned values only after lookup, when validating the selected compiler input and evaluating `grid_cpp`. Extend `test_spec_key_is_never_coarser_than_triton` with a tuning-key invariant, and verify that removing the exact-value field makes that test fail.

The frozen `RenderContext` and `ModuleKey` include an autotune-mode discriminator, ordered tuner-key names, config-name/type schema, and generated grid source. Candidate values, tuner identity, and winners are runtime state, not generated-code identity. One generated extension may serve several bound launchers, but each bound launcher owns its own kernel cache, compile callback, original-tuner reference, and private selection cache. The existing module-state callback remains for raw-JIT launchers. C visits and clears these bound Python references during GC.

At factory construction, copy configs and their mutable `kwargs` into owned `Config` instances, preserving candidate order and each kwargs insertion order for Triton's tie-breaking and disk-cache identity. Freeze the raw JIT reference, ordered `keys`, `arg_names`, `cache_results`, fixed options, relevant knobs, JIT source key, and ordered candidate fingerprint into the private tuner; a shallow copy that still reads mutable fields from the original is insufficient. Each device-bound launcher gets an independent private tuner/cache; no process-global selection registry is needed. The original tuner reference is used only for visible `best_config` and timing attributes. Later mutation of the original configs or `tuner.cache` does not alter an existing bound launcher's winners. A new `make_launcher` call captures changes; Aiter's handle-factory key must include the ordered config fingerprint. The original `tuner.cache` is neither consulted nor updated by native selection, and clearing it does not reset native winners. Use a fresh original-tuner cache when comparing candidate calls with Triton; changing KDA's old keyword-call order to canonical native argument order can miss an existing disk-cache entry and retune once.

Each native cache record owns the winning `CompiledKernel` and a private snapshot `Config` even when `return_compiled=False`, plus its function pointer, block size, shared bytes, packed-argument count, and immutable grid-needed config scalar values. A separate display `Config` copy may be exposed through the original tuner's `best_config`, but neither launches nor grid evaluation read that mutable view. This extends record GC traversal and teardown beyond the current `INTJ_RETURN_COMPILED` case. The record, rather than a temporary Python callback or the original tuner's cache, keeps the GPU function handle alive. `return_compiled=True` returns a new reference to that record's object on every call.

## Cold and warm execution

On a native cache miss, C passes the bound callback `(key, packed_count, device, stream, grid controls/extras, *current_public_JIT_args)`. Baked fixed values live in the callback snapshot; bound tensor/pointer values are outside this subset. The callback requires the requested device and stream to be current, and rejects a cold miss during graph capture. It reconstructs the complete JIT call as keywords in JIT declaration order, without config-owned constexprs. This defines a stable dtype order for Triton's private tuning key; an old keyword call may use another order. For `grid_arg`, it passes the supplied dimensions to Triton. For `grid_cpp`, a Python grid adapter calls the extension's cold-only C grid evaluator with current arguments, extras, and each candidate's config values.

Under a per-bound reentrant lock and an in-progress marker, a private clone of the tuner runs Triton's normal candidate benchmark and disk-cache logic via `private_tuner.run(..., grid=grid, warmup=False)`. A wrapper around its `_bench` marks candidate phase and clears the mark in `finally`. A temporary inner runner, with `.fn` pointing to the raw JIT for Triton's disk-cache unwrapping, uses the original `JITFunction.run` for candidate launches and overrides only the final selected call to `warmup=True`. It returns the `CompiledKernel` without a final Python launch. Passing `warmup=True` to the whole `Autotuner.run` would benchmark compilation instead of execution. This handoff was checked with a two-config GPU probe under Triton 3.7.1 and 3.8.0. Refuse reentrant selection in the same bound launcher before benchmarking; a second thread waits and then observes the first winner. On a private selection-cache hit with a new intj specialization, compile only the selected config. An exception installs no native record and clears the private run's transient state.

Before the final warmup, require the selected config to match the immutable fingerprint of one validated candidate, including when Triton loaded disk timings. Validate the selected kernel's complete compiler input, target/device, parameter order and count, and intj's existing scratch, CTA, cooperative-grid, and PDL restrictions; initialize its function handle on the current device. Copy `bench_time` and `configs_timings` from the private tuner to the original tuner after a cold selection, where Triton produced them. Return the kernel and private config snapshot to C. C rechecks its own cache after the callback; if another miss installed the key, it uses that **winning record's** config and compiled object. It then evaluates the selected grid and makes exactly one final launch on the supplied stream. For `grid_arg`, any zero dimension returns `None` immediately when `return_compiled=False`. If a selection already exists, a new specialization may compile and then skip its final launch on a zero grid. Before tuning a new key, evaluate every candidate grid and refuse any zero dimension (including a disk-cache hit): Triton would benchmark no work for that candidate. Check dimensions individually, never by multiplying them into a possibly overflowing product. A selected zero grid returns the compiled object when requested.

On a hit, C decodes current arguments, probes its existing native kernel cache, reads immutable config values from the record, evaluates `grid_cpp` in C after lookup, and launches. There is no Python tuner/grid callback, rebuilt tuning tuple, or second launcher lookup. C sets the original tuner's `best_config` to the record's separate display copy on each call, including after the cache recheck. Treat that view as read-only: mutating it may make its displayed fields stale, but cannot change the launched kernel or grid. It need not have object identity with an entry in the original mutable `configs` list. No per-launch config hook is supported. As with today's bound intj launcher, a hit trusts that the bound device is current and tensor pointers are accessible; callers must enforce that contract before native calls. A warmed bound launcher may be used during graph capture and replay on its supplied capture stream.

## KDA integration and acceptance

Aiter's default FlashKDA K1 and K2 each use one pinned config: gfx950 publishes six K2 candidates, but `autotune_configs` returns one fallback while `CHUNK_DELTA_ATTN_TRITON_AUTOTUNE` is off. Opt-in tuning gives K1 four and K2 24 candidates; a test also installs the six published K2 candidates. Keep the current single-config raw-JIT path. Once native autotuning is implemented, replace the temporary decorated-Triton multi-config branch with `make_launcher` on K1's inner tuner (passing explicit heuristic flags) and K2's tuner (`segment_grid` and current `num_segs`). Continue passing current tensors, grid extras, device, and stream on every call, and keep the single-config path's per-forward current-device and pointer-accessibility validation. Replace KDA's test that clears and inspects `tuner.cache` with a fresh-bound-launcher test of native key separation and selection counts.

Acceptance requires: (1) a fresh-cache comparison with Triton using deterministic candidate scores that benchmarks in the same order and picks the same config for two keys with different `BW`/`num_warps`; (2) native keys that separate K2 `NUM_SEGS_CLASS` values despite identical JIT specialization, plus dtype and alternating-key checks; (3) one final launch on a cold miss and no Python tuner/grid callback on hits, with the returned compiled object kept alive; (4) correct current tensors, cache-recheck winner, zero-grid behavior, graph replay, and tests under Triton 3.7.1 and 3.8.0; (5) matched gfx950 opt-in KDA correctness and warmed full-forward host timing against `_FastLaunch` and the temporary decorated path, with a repeatable regression beyond run-to-run variation blocking replacement. Unsupported input, config, and hook cases must raise `UnsupportedKernel` before a native GPU launch whenever they can be identified at construction.
